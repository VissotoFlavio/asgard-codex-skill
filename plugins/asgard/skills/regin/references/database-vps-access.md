# VPS container database access

Use this contract when a database runs in a container on a remote VPS. It grants no connection, credential, network, container, database, or mutation authority.

## Route and ownership

Keep the database private. Prefer no published database port; when host access is required, bind it only to the VPS loopback address. Public or wildcard publication such as `0.0.0.0` or `::` is forbidden by default. An exception requires explicit Ymir-owned network authority, exposure analysis, firewall restrictions, encryption, verification, and Heimdall approval.

Ymir owns the verified SSH destination, host key, approved SSH identity reference, remote principal/access level, SSH agent/config, local forwarding, Docker/Compose port binding, firewall, connectivity, and external credential mechanism. Regin owns database identity checks, structural discovery, database principals/grants, versioned migrations, and authorized validation or application. Neither role inherits or grants the other's authority.

Use a local SSH forward from an exclusively bound loopback-only ephemeral or approved local port to the VPS loopback database port. Reject occupied or stale listeners and IPv4/IPv6 wildcard or dual-stack exposure. Require host-key verification and confirmed forward establishment, verify the listener belongs to the bounded tunnel and reaches the resolved destination, and record the actual allocated port. Select only the approved host-scoped SSH identity, verify the effective remote principal and access level, and fail closed on key, user, privilege, endpoint, or ownership drift. Prohibit remote/public listeners and agent forwarding unless separately justified, and close the tunnel after the bounded activity. Record only aliases, ports, non-secret identity evidence, and timestamps.

## Credential separation

SSH identity and database credentials are independent. Resolve them through SSH agent/config, an OS keyring, or a provider vault using opaque references. Never place secret values, private keys, passwords, or connection strings in repositories, profiles, inventories, prompts, command arguments, process environment, reports, logs, traces, or child processes. Deliver database secrets through provider-native authentication, a keyring API, protected stdin/file descriptor, or a private temporary file when the adapter supports safe cleanup; disable echo/tracing, remove transient material, and fail closed when only literal argv/environment delivery is available.

Use distinct database principals for application runtime, read-only `DISCOVER`, isolated `VALIDATE`, migration `APPLY`, and emergency administration. Each receives phase-scoped least privilege. Runtime credentials never authorize Regin. Ymir owns external secret creation, storage, delivery, rotation, and revocation; database `CREATE ROLE`, `GRANT`, `ALTER`, and `REVOKE` are Regin `APPLY` mutations through a declared adapter. Coupled changes require both exact authorities; neither substitutes for the other, and Ymir never grants database authority.

Owner/superuser and emergency identities are blocked by default. A break-glass exception requires exact Ymir credential-mechanism authority and exact Regin operation authority bound to phase, candidate, target, minimal scope, and short expiry. Verify the effective principal, produce redacted audit evidence, revoke or expire access immediately afterward, and restore the default block. Missing authority, expiry, revocation, or drift fails closed.

A profile may record VPS profile alias, approved SSH identity reference, expected remote principal/access level, tunnel mode, local and remote loopback aliases/ports, database endpoint alias, credential mechanism, opaque references per phase, and non-secret credential generation/version or provider change token. Resolve credentials freshly and invalidate evidence on rotation or revocation even when the opaque reference is stable. Never copy a secret from the VPS or container into local state. Container secret names may be inventoried only when needed; secret contents and environment values remain prohibited.

## Connection and failure gates

Before opening transport, Ymir verifies the expected VPS/host key, approved SSH identity reference, requested remote user/access, requested destination, and local-port availability. After SSH authentication and confirmed forward establishment, Ymir verifies the observed remote principal/access, actual listener ownership, exclusivity, loopback address and allocated port, plus the resolved destination. Only then may the database session be established. Before each database phase and immediately before `APPLY`, Ymir also verifies the Compose project/service or container identity, image digest/version, network, and exact host-to-container bindings. After the authenticated database session is established but before any database operation, Regin verifies environment, database/catalog, schema/tenant, engine/version, effective principal/role, current grants, credential generation, and authorized phase; mismatch closes the session without operation. Any absent, mismatched, unexpectedly overprivileged, public, or unverifiable value fails closed, except an active exact break-glass grant.

Tunnel establishment authorizes no database operation. `DISCOVER`, `VALIDATE`, and `APPLY` remain separately authorized. Immediately before `APPLY`, repeat both infrastructure and database identity checks against the exact candidate. Tunnel loss, host-key change, container replacement, port-binding drift, credential reference or generation change, rotation/revocation, principal/grant change, or unexpected privilege invalidates evidence and authority. Halt, close access where safe, rediscover, and require fresh authority; never automatically retry a mutation.
